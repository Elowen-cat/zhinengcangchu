- 模式：refinement；阶段：仓库边界已由用户明确，多人协作与分析范围正在收敛，未开始改造。
- 更新：2026-10-11。
- 代码依据：LZY426915/don-tRun，提交 3d24b8a（2026-09-11）。本次静态阅读，未构建 APK、未实机测试、未调用付费模型。
- 目标：判断是否适合以现有 Android 应用为基础参加 2026 仓颉杯，并识别商业产品与开源参考。
- 主观方向评分：聚焦门店后仓工作流 7/10；仅换场景与界面 3/10。这不是获奖概率。若取得真实门店验证可上调；若操作更慢、账务不可靠，应下调。

## 初步判断

建议继续验证仓储方向，优先考虑便利店或小型食品门店后仓。定位假设：帮助店员用手机完成收货录入、批次效期管理和准确找货，减少录入与查找成本。药店作为有真实合作对象时的备选，不同时覆盖多个行业。

商业需求可能比个人收纳更高频、收益更容易计量，但现有系统竞争更强、数据正确性要求更高。这是推断，不代表已完成用户需求验证。

## 已有基础与缺口

静态代码确认：Kotlin/Compose、Room 本地存储、多级位置、物品数量/单位/有效期、图片识别、语音转写、智能体工具调用、修改后读取验证、部分危险操作确认、备份恢复与到期提醒。

Item 当前将物品名称、单一数量、位置、到期时间及使用状态放在同一实体；AppDatabase 只有 Item、Category、Location、AiModelConfig 四种实体。服务端主要是模型和天气代理及安装会话鉴权，不能视为门店员工账号与库存共享后台。

当前未见独立 SKU、批次、库存流水、收货/出库单、员工角色、跨设备共享库存及并发库存处理的领域实现。改造必须触及库存业务，而不只是文案。

特别风险：图片识别提示词会根据常见习惯推测位置，并返回相对今天的 expireDays。商业库存应区分识别候选、上架建议与实际已确认库位；效期应基于标签日期与明确规则核验。普通商品条码不能默认唯一标识批次与效期。

## 建议验证的核心体验

在一家门店中：扫描商品条码或拍摄清晰标签，结合语音生成收货草稿；对规格、批次、数量、单位、效期做匹配和缺失项追问；人工核对后落库；之后能查到具体批次与库位，并完成有记录的取货或移库。

AI 承担非结构化输入理解、商品匹配和歧义澄清；库存计算、效期比较、权限、负库存约束及执行留痕由确定性逻辑保证。临期优先出库本身属于业务规则，不能包装成 AI 独有创新。

## 成功指标与停止条件（建议值，未获用户确认）

- 最小验证：真实店员和真实或经脱敏的商品样本；用同一组任务对比现有录入方式，不能只和故意繁琐的流程比较。
- 成功目标：至少 30 个覆盖不同规格、批次和模糊标签的任务；中位完成时间降低至少 30%，确认后的库存结果全部正确；另报模型原始识别错误率、修正率和执行失败率，避免只报告确认后的正确率。
- Aha 时刻：店员一次输入生成可核对的收货草稿，随后按真实库位和批次完成找货，库存流水对应一致。
- 收缩/停止条件：若 48 小时内既找不到场景验证对象，也无法取得有代表性的输入样本，不锁定行业痛点；若含修正的总耗时不优于原流程，或出现静默记错批次/重复扣减，暂停扩展功能并重新评估核心交互。
- 以上数字均为建议验收阈值，不是已取得的实验结果。

## 范围建议与改造约束

- 建议范围：单门店、收货、SKU/批次/效期/库位、出入库留痕、手机多模态辅助、人工确认。
- 暂缓：完整 ERP、财务、会员营销、医保处方、复杂需求预测模型、机器人、整架拍照自动精确盘点、全国多店协同。新增考虑可解释的出库趋势和补货测算，见本轮更新。
- 保留能力建议：已有手机拍照/语音入口、多级位置浏览、真实数据查询、写后核验、备份恢复。
- 明确重新设计：家庭“用完/评价”生命周期；直接覆盖数量和位置；根据习惯猜实际位置。旧数据迁移需保留名称、图片、数量、单位、位置路径和效期，不得默默丢失。
- 预演失败：功能铺太大拖过截止；AI 猜错规格或单位却直接入账；重复请求导致重复扣库存；两个终端各有一套账；接已有 POS 后仍要求重复录入。后续选型必须针对这些情况验证。
- 设计定位：工作工具，清晰、操作少、错误可见比装饰重要。
- 商业模式、实际客户、部署环境、团队人手：未知。本轮以竞赛原型为目标，不虚构营收或市场规模。

### 一人时的止损线和技术条件

- 先用一天完成 3—5 个校园用户/管理员的短访谈或流程观察，确认一个反复出现的问题。可问：最近一次找不到/买晚了/交接不清的物品是什么？现用表格或聊天记录怎么处理？大约多频繁？可否让你按现有物品做一次演示？
- 若只能联系普通同学，找能管理社团器材、实验室耗材、竞赛队设备的人，而不是只问“你会不会用这个 app”。需要具体事件，不是礼貌性点赞。
- 如果观察不到真实痛点，优先把现有项目打磨为可运行的智能物品管理原型，解释 AI 如何安全操作本地真实数据，不做未经验证的“行业级 WMS”主张。
- 若决定新增多人协作，必须验证后端部署、账号隔离、共享数据和服务端权限。现有代理服务不是库存后台。不要把只有 UI 的团队切换假象称为协同功能。
- 作品标签清楚区分真实观测、匿名/脱敏样例和模拟数据。用模拟数据演示是可接受的原型方法，但不能伪报真实用户测试或收益。

## 本轮收敛：多人协作与采购分析（2026-10-11）

### 用户已明确的边界

- LOCKED：聚焦仓库内的库存与作业，不追踪售卖区商品状态。来源：用户本轮明确表述。
- 用户希望评估工作组、成员权限、出库数据统计、采购价格变化、进货建议和定价分析。尚未指定角色体系、算法或完整一期范围。
- 限制：距章程截止约 12 天，需要成熟且有新意的可运行应用。

### 推荐核心定位（待认可）

面向小型门店后仓的多人协作与采购决策助手：店员产生可信的库存流水，负责人依据真实出库需求、库存、在途、效期与供应商报价生成可解释的补货草案，确认后继续跟踪采购和收货。

价值闭环：多人收发货 → 统一库存流水 → 风险和补货建议 → 负责人确认草案 → 采购在途 → 收货入库。采购单只在本系统登记，不自动向供应商下单。

### 数据能力边界

1. 仓库向售卖区发货不等于终端销售。售卖区作为出库去向标签即可，不纳入系统库存。分析使用“出库需求”和“仓库覆盖天数”，不声称消费者销量或全店库存。
2. 出库须分正常领用/配送、调拨、报损、退供应商等；报损及内部移库不能混入需求。缺货日、异常大单、退库和历史迁移须标识，避免将被库存限制的出库量误读为真实需求。
3. 采购历史价不等于市场价。当前报价须来自人工录入、单据上传或供应商报价导入，保留时间、来源、规格、单位、税运费口径、起订量与交期。过期报价标识并请求更新。
4. 本期可做成本和目标毛利率测算；缺少真实售价、销售量和价格变化后的反馈，不能计算利润最优售价或价格弹性。无需管理售卖区也可手动填写拟售价做情景测算，但这不构成销售预测。

### 必须先成立的成功指标与收缩条件

建议验收目标，非已测结果：
- 两台设备用不同成员账号完成同仓收发货；库存和流水对账正确。
- 并发不足库存、重复提交、超权限和跨工作组请求均有服务端验证；出现静默错账则禁止扩展分析功能。
- 补货草案中每个数量、价格、日期可追溯到计算和来源；至少覆盖数据不足、报价过期、到货前缺货、批次临期、预算不足五类情况。
- 真实数据足够时，与人工固定阈值/近期平均需求基线比较；没有真实历史时只验证计算、工作流和异常处理，不宣称降低缺货率或提高利润。
- 建议到 10 月 15 日仍不能完成可靠的两机出入库时，砍掉报价图片解析、价格情景比较等扩展，保留协作库存和基础风险解释。

### 范围建议

P0：
- 工作组：一组一仓，创建/加入/移除成员；固定管理员、仓管员、只读成员三种角色。成本及采购审批权限集中到管理员，后端统一校验，前端仅负责呈现。
- 库存：商品、批次、库位、基本单位及固定包装换算；收货、出库、移库、盘点差异/冲销记录。已过账流水不可直接删除，纠错产生关联更正记录。
- 单据：采购草稿/已确认/部分收货/完成/取消等最小状态，未完成数量形成在途，避免重复建议采购；审批时重新检查库存和报价版本。
- 分析：有效出库趋势、覆盖天数、临期/低库存、采购价变化；初期采用可核对的统计和规则计算。
- 智能体：复用语音/图片基础，解析请求、调取允许访问的数据、追问不确定项、呈现带依据的补货草案；不能绕过权限直接修改库存。

P1（P0 通过后再做）：供应商报价图片生成待确认草稿；目标毛利率/拟售价成本测算；更多图表和导出。

不做：完整 POS、售卖区库存、财务总账、自动市场价格爬虫、自动调价、自动外部采购、复杂角色设计器、复杂离线写入同步、多仓网络、深度预测模型、整架照片自动精准计数。

### 高层技术约束

- 保留 Kotlin/Compose、现有相机语音与代理能力，避免临近截止更换客户端技术栈。
- 共用服务端库存数据库为唯一记账依据；Room 用作读取缓存和未提交草稿。首版离线可看缓存/存草稿，不将其展示为已入账。
- 库存提交须具备原子性、重复请求防护、负库存检查和成员权限；库存改动与流水一起成功或失败。
- 统计计算由程序产生；模型负责语义理解、调用、解释和方案沟通。模型不直接做权威金额/数量计算，不生成无来源的市场价。
- 价格记录保留每次变动，不能用新进价覆盖旧批次成本；统一税运费和包装单位口径。
- 不把每次价格上涨解释为应该囤货，需同时检查预算、交期、起订量、效期与历史需求不确定性。

## 2026-10-11 本轮产品链路梳理（推荐方案，覆盖前述相互冲突的范围草案）

### 产品边界

暂定为：**小型门店后仓库存与补货决策助手**。只管仓库/后仓，不管售卖区和 POS；本届按一台设备、单人操作的完整原型做扎实，不声称云端多人协同或真实商业预测。首选便利店/小超市后仓作演示，暂不选药店，以免引入药品专业追溯和经营要求。

### 一条可演示的闭环

1. 配置商品、基本单位/整箱换算、库位，并录入一个或多个库存批次；批次分别保存数量、效期和本次进价。
2. 收货入库：拍照或语音可预填商品、批次、数量、效期、供应商及进价；操作者核对后确认，生成入库流水并增加对应批次可用量。
3. 后仓出库：选商品/批次、数量和去向/原因（如补到货架、损耗、退供），系统先校验可用量，再生成不可静默删除的出库流水并扣减批次数量。按先到期先出（FEFO）提示优先批次，允许人员核对。
4. 工作台根据真实本地记录列出临期批次、低库存、最近出入库和待处理事项；通知直接进入对应商品/批次。
5. 分析页展示按原因区分的后仓出库量、近期变化、库存覆盖估算、临期损耗风险、进价历史。出库到货架不是消费者销售，报告不得标成销量或全店需求。
6. AI 使用工具查询真实库存和流水，生成有依据的补货草案：说明可用库存、有效出库均值、确认在途、交期/起订量与报价来源，供人修改确认；确认后登记采购计划，实际到货再回到第 2 步。首版不自动下单。

### 现有资产的处理

- **直接保留技术底盘**：Kotlin、Compose、MVVM、Hilt、Room、Navigation、WorkManager、现有 Android 构建链和可运行 APK。
- **保留并改造成仓储能力**：商品名称/分类/单位、数量、价格、效期、图片、备注；多级 Location 树；相机/多图、语音输入、自然语言查询、AI 调用与工具确认；本地到期通知、备份恢复。
- **调整而非照搬**：当前 `Item.quantity` 是一条物品记录上的当前数量，没有批次、库存流水、入库/出库/移库原因、确认在途和权限/成员表；因此它可以迁移为 SKU/商品主数据或期初库存，但不能直接充当批次账和流水。需要新增批次与库存变动记录，再重做相关 DAO、统计和测试。当前库存主体保存在 Room；现有模型代理不等于共享库存服务。
- **UI 可统一重做**：改品牌、颜色/字体/组件、导航标签、首页层级、空状态、示例数据和文案。优先重做工作台、库存/批次列表与详情、收货/出库、分析/AI建议；设置、回收站、备份等可延后。设计目标是清晰、少误触、扫描式读取，而不是保留家庭应用的渐变毛玻璃布局。
- **从主流程移除或隐藏**：天气、物品用完后的评分、家庭/宿舍措辞、衣物天气建议和购物清单；回收站可保留但不是演示重点。

### 创新点保留顺序

1. **主打：AI 解释式补货建议**。数字由本地/程序规则计算，模型负责理解问题、调工具、解释依据和形成待确认草案。有效后仓出库量作为仓库补充节奏的代理；不得称为消费者销量或利润最优预测。历史太少时显示“样本不足”，降级为低库存规则。
2. **支撑：批次、效期和 FEFO 作业**。让临期风险与具体库位、数量和出库动作相连，而非只有通用提醒。它是可靠的领域工作流，但单独不是强创新。
3. **可保留的小范围采购价格分析**：由用户手动录入/导入带日期和规格的历史进价/供应商报价，对比含包装、起订量、交期等条件的补货方案。没有实时来源时不得叫“市场价”。时间允许再做一屏报价比较，不先做图片 OCR。
4. **定价只留为可选成本情景计算**：根据人工输入的成本和目标毛利率算出参考挂牌价；不声称 AI 找到最佳售价或预测销量。只有主闭环稳定后才做。
5. **多人协同延期**：成员权限、跨设备同步、并发记账作为后续路线，不以角色切换 UI、同机模拟账号或静态演示冒充真实协作。

以上是单人参赛的建议范围。若截止前只完成“批次 + 流水 + 临期工作台 + 可追溯补货草案”，项目仍有完整的数据闭环和可讲清的 AI 创新，不必靠堆很多未落地的模块来显得丰富。

## 2026-10-11 截图审阅：仓储版 UI 改造清单

### 全局视觉与导航

- 当前紫橙渐变、大面积毛玻璃、悬浮导航和大量留白有亲和感，但会弱化库存表格/告警的可读性。改为浅灰工作底色、白色内容卡、深色正文、单一品牌强调色；临期用琥珀、低库存用橙、缺货/过期用红、正常状态用绿，并同时显示文字/图标，不能只靠颜色。

- 示例数据要形成一眼看懂的业务状态：正常批次、临期批次、低库存商品、近期出库、两家报价/不同交期。若非真实业务数据，应全程标注“演示数据”。当前截图仅一件感冒药，空态和零值多，不能用于表现库存分析与补货建议。

### 按截图页面修改

1. **首页 → 工作台**（截图 `164423`）：移除“东西不跑”大渐变欢迎区和“最近添加”为主的家庭首页。顶部改为仓库名/日期/本地数据状态；首屏放临期批次数、低库存 SKU、待收货/待盘点、今日后仓出库等可操作指标；紧接“收货、出库、盘点”快捷入口及风险任务列表。首页要在首屏回答“现在最需要处理什么”，不要先讲品牌故事。
2. **库房 → 库存**（截图 `164614`）：移除“全部物品 / 已用完 / 待评价 / 已评价”家庭物品生命周期筛选。改为“全部 / 低库存 / 临期 / 缺货”筛选，旁边提供品类、库位和批次条件。每行/卡片优先显示商品名/SKU、可用量+单位、批次数、最近效期、库位与库存状态；列表更紧凑，不要当前大卡片后大块无信息留白。顶部搜索说明可搜商品、批次和库位。

4. **我的**（截图 `164636`）：移除“东西不跑用户 / 记录生活中的每一件物品”。单人本地原型可改为“仓库与设置”，展示仓库基础信息、预警阈值、单位规则、数据备份、AI 服务状态、关于/开源来源。只有真实实现了登录和云端成员服务后再放“工作组/权限”。“库存估值 ¥0.00”若成本缺失会误导，应改为“未录入成本”或隐藏；首页已有的经营指标不必在设置页重复展示。

## 2026-10-11 导航原型与 Compose 实施约束

### 点击路径

| 起点 | 可点区域 | 目的页/动作 | 返回行为 |
|---|---|---|---|
| 工作台 | “临期”指标/临期任务 | 库存列表，自动筛选临期批次 | 返回工作台并保留滚动位置 |
| 工作台 | “低库存”指标/低库存任务 | 库存列表，自动筛选低库存 | 返回工作台并保留滚动位置 |
| 工作台 | 收货/出库/盘点快捷项 | 对应作业表单 | 提交成功后到单据详情，再返回来源页 |
| 库存列表 | 商品行 | 商品库存详情（汇总可用量、批次、流水） | 返回原筛选和原位置 |
| 商品详情 | 入库/出库/移库 | 对应单据表单，自动带入商品及可选批次 | 保存后回商品详情并刷新库存 |
| 商品详情 | 某个批次/流水 | 批次详情或流水详情 | 返回商品详情 |
| 分析 | 某个趋势/告警卡 | 对应明细列表及所用统计区间 | 返回分析并保留期间选择 |
| 分析/工作台 | AI 补货建议卡 | 补货建议详情与数据依据 | 返回来源页 |
| 补货建议详情 | 生成采购草案 | 草案预览/编辑 | 保存后进入草案详情或列表；不自动下单 |
| 任一主页面 | 底部中央“＋” | 底部快捷操作面板：收货、出库、盘点、移库 | 点空白/返回即关闭面板 |

底部主导航固定为“工作台、库存、分析、我的”。表单和详情页隐藏底部主导航，使用顶部返回键，减少误触；切换主导航时保存各页状态，返回详情后保留筛选、滚动位置和图表时间范围。

### 可实现性控制

- 当前项目已用 Compose Navigation，也有 Haze/玻璃面板组件，可在原架构里替换主题和页面；无需换技术栈，也无需把整套 UI 写成自定义绘制。
- 液态玻璃只用于工作台概览条/快捷操作浮层等少数区域：半透明表面、细描边、淡淡的高光即可。库存数字、效期、表单和确认按钮用不透明底，确保对比度。优先复用当前 `GlassPanel`/Haze；限制模糊面积，避免额外阴影层和每帧动画。
- 图标统一采用一套 Material Symbols/Material Icons Outlined，统一 24dp 尺寸、描边和选中态。库存告警用小图标+文本标签；只有少量专属功能再做简单 Vector Drawable，不把生成图片当功能图标。
- 页面转场用 Navigation Compose 默认导航加轻量约 150–200ms 的淡入/横向滑入即可；主导航配置单实例和状态恢复，避免每次切换重复建页面。复杂共享元素转场、3D、持续模糊、粒子动画暂不做。
- `收货/出库/草案`统一使用 Compose 表单组件、数量步进器、批次选择器和底部固定确认区；库存写入都经 ViewModel/Repository，并由库存流水驱动状态，UI 卡片不能直接改当前数量。
