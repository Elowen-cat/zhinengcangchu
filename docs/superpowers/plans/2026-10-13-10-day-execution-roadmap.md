# 十天改造执行计划

## 目标

在十天内把现有应用整理成一条可现场演示、数据可信的单仓库存闭环：

**商品入库草稿 → 人工核对 → 批次库存增加 → 选择批次出库 → 库存流水 → 单品补货分析。**

这十天优先交付稳定的本地单仓版本。多人跨设备协同、云端账号权限、市场价格抓取和完整 ERP/POS 不纳入本轮验收，避免做出看似有入口、实际不可靠的功能。

## 源码保留与 API 边界

- 这是在现有项目上的渐进式大改，不重建空项目。保留 Kotlin/Compose、Room、Hilt、相机、图片处理、录音、通知和备份等可复用基础。
- 旧家庭收纳页面、`Item` 数据表和 ViewModel 先保留。新仓储页面使用单独 screen / route / 组件；确认新链路稳定、数据迁移和备份通过后，再决定旧入口何时退场。
- 不编辑 `server/`，不部署、不改动、不请求组长修改现有云函数。现有 `BackendApiClient` 仅作为旧 App 接口入口留档；仓储新流程暂时不依赖旧端点。
- 临时停用远程 AI 时只做 App 侧隔离：新仓储流程不注入旧 API 客户端，识别不可用时落到人工录入/核对。等你自己的云函数就绪，再通过单独的 API 接口适配层接入；不要把服务商地址、鉴权或业务判断散落到 UI。
- 今晚先做可视化切片：新建仓储语义色和 Compose 页面壳层，做工作台第一屏并用 Preview/开发样例检查布局。样例数据只用于预览，不作为正式库存数据。

### 现有代码复用判断

| 保留或复用 | 处理方式 |
| --- | --- |
| `CameraScreen`、CameraX、`ImageUtil` | 保留拍照底层；仓储识别结果改走新草稿界面，不直接沿用家庭物品保存动作。 |
| `WavAudioRecorder` | 保留录音底层；语音转写服务通过独立接口接入，未接好时仍允许手动录入。 |
| `AppDatabase`、旧 `Item`/分类/位置表、旧 DAO | 不删不覆盖；增加仓储实体和迁移，逐步转移演示链路。 |
| 通用卡片、图片预览、日期选择等 Compose 组件 | 按职责筛选复用；紫色专属样式通过新组件绕开，避免一次性改坏所有旧页面。 |
| `BackendApiClient` 和组长的云函数 | 新仓储流程先不调用；后续由自己的 API adapter 替换接入，不改云函数源码。 |

## 必须遵守的产品规则

- 待确认单据不改变库存；用户最后确认后，才一次性写入库存变化和流水。
- 数量按“商品—批次”管理。批次记录数量、效期和库位；商品记录名称、分类和基础单位。
- 出库必须选批次并校验现存量；临期批次优先提示，损耗出库不计入补货需求。
- “销售区”只作为货物去向记录，不代表应用跟踪了售卖区库存或真实销售。
- 补货建议使用可解释的本地规则，不包装成 AI 决策或最优定价。采购价格只比较已有的供应商历史记录。
- 图片/语音只生成可编辑草稿；不能自动确定批次、效期、库位或直接改库存。
- 老版本家庭物品数据保留原表；迁移失败不得清空旧数据。

## 固定演示数据与补货口径

先用一个稳定样例贯穿截图和演示：鲜牛奶 250ml，基础单位“瓶”；近期有效出库 14 天共 56 瓶，即日均 4 瓶；当前库存 24 瓶；安全库存 8 瓶；目标覆盖 7 天；无待入库数量。建议量为：

`max(0, 日均有效出库 × 目标覆盖天数 + 安全库存 − 当前库存 − 待入库数量)`

因此示例为 `4 × 7 + 8 − 24 = 12 瓶`。覆盖天数约为 `24 ÷ 4 = 6 天`。文案需标明这是基于仓库有效出库记录的估算，不代表消费者销量或市场价格预测。

## 范围取舍

### 十天内必须完成

- 本地单仓商品、批次、库存流水和待确认单据。
- 手动入库、手动出库，以及确认时的库存校验。
- 工作台、库存/批次详情、补货汇总/商品分析四条主要页面路径。
- 一个可信的数据库升级路径和数据备份兼容检查。
- 一条可重复、无网络依赖的现场演示流程。

### 有时间才完成

- 拍照和语音都接入统一草稿流；如果时间不够，先保证其中一条完整，其余入口降级到手动核对。
- 图表动画、复杂液态玻璃效果、更多筛选项和非核心个人设置。
- 历史进价对比卡片；仅在样例数据真实完整时展示。

### 本轮明确不做

- 多设备实时协同、账号体系、角色权限和云端库存同步。
- 售卖区库存、POS 销售、市场价格爬取、自动定价和“AI 自动采购”。
- 多仓、复杂包装换算、供应链/财务管理。

## 每天的完成判定

每天收工前只检查三件事：当天验收项是否通过；旧主流程是否仍能启动；未完成项是否会阻塞收货—核对—出库—分析主链。非阻塞的视觉细节进入待办，不挤占数据正确性和最后两天的稳定时间。
